## 🚀 Cómo ejecutar

```powershell
npm install            # solo la primera vez
npm run dev            # server (:3000) + client (:5173) en paralelo
```

- App: `http://localhost:5173` · API: `http://localhost:3000/api/v1`
- Usuarios (clave `Gaby2026*`): `admin` (todo) · `bodega` (entregas) · `cocina` (monitor) · `auditor` (lectura)
- PostgreSQL 16 local, BD `sistema_gaby`. Credenciales en `server/.env` (no versionado). La contraseña del usuario `postgres` fue restablecida el 2026-07-06 y vive solo en ese archivo.
- Comandos útiles: `npm run db:migrate` · `npm run db:seed` · `npm run db:studio` · `npm run typecheck`
- Pruebas unitarias + integración (Vitest, Fase 14): `npm test` (= `npm run test -w server`) — requiere la BD de prueba `sistema_gaby_test` sincronizada una vez con `npm run test:db:push -w server`. No requiere el dev server corriendo.
- Pruebas E2E de negocio (todas): `npm run test:e2e` desde la raíz — corre los 9 scripts `scripts/test-*.mts` en orden y agrega un resumen único (requiere `npm run dev` corriendo). También se pueden correr sueltos: `npx tsx scripts/test-9a.mts` · `test-9b.mts` · `test-9c.mts` · `test-10.mts` · `test-11.mts` · `test-12.mts` · `test-13.mts` · `test-19.mts` · `test-realtime.mts` (son re-ejecutables — `test-13.mts` crea un respaldo real de la BD en cada corrida, no ejecuta una restauración real)
- Build de producción (Fase 15): `npm run build -w client` genera `client/dist`; con `NODE_ENV=production` el propio server (`:3000`) sirve esos estáticos + fallback SPA en el mismo puerto — no hace falta Vite en producción.
